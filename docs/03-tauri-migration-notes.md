# Tauri移植に向けた方針・論点(実装前のすり合わせ用)

前提: [01-architecture-analysis.md](01-architecture-analysis.md)・[02-feature-analysis.md](02-feature-analysis.md) の分析結果を踏まえ、PC向けTauriアプリとして作り直す際の設計方針・スコープの選択肢を整理する。**このドキュメントの時点ではまだ実装しない**（ユーザー指定どおり、まず分析結果の共有が目的)。

## 1. 現実的なスコープ設定が必要

元アプリは smali クラスファイル約29,000個規模の商用製品で、以下の要素を含む:

- 独自の文書エンジン(df/nt/un)とバイナリファイル形式(.atdoc)
- ネイティブ実装の手書き文字認識エンジン(mazec、複数言語の有償アドオン)
- 独自プロトコルによるリアルタイム教室協働編集(クラウド仲介+ソケット通信)
- 自社クラウドバックエンド(Cabinet同期、Collabo、認証、課金)
- PDF独自パーサ/ライタ、動画トランスコード、WebDAV連携等

**フルパリティでの再実装は現実的ではない。** 既存の `metamoji/`(Tauri v2 + React + TypeScript + Viteの初期テンプレート、未カスタマイズ)をベースに、優先順位をつけたMVPスコープを決める必要がある。

### スコープの選択肢(例)

- **A. スタンドアロン・ノートアプリ**: クラウド同期・教室協働なし。手書き/テキスト/画像/PDFでノートを作成・保存・PDF書き出しできる単体デスクトップアプリ。最も現実的な第一段階。
- **B. Aに加えてクラウド同期**: 自前のバックエンド(新規設計)を用意し、複数デバイス間でノートを同期。
- **C. Bに加えて教室協働機能**: リアルタイム配信・モニタリング・アンケート等の「Share Classroom」らしさを再現。開発規模が大きく、サーバーサイドの新規構築が前提。

## 2. 再利用できる設計 vs 作り直しが必要な設計

| 要素 | 方針 |
|---|---|
| ドキュメント階層(Document→Note→Page→Layer→Unit)、Unitごとの型タグ+プロパティ辞書という考え方 | **設計思想はそのまま踏襲可能**。実装は新規(Rust/TypeScriptで型付きモデルとして定義) |
| ストロークデータモデル(点列+時刻+筆圧、順序付きストローク、スタイル) | **設計をそのまま流用可能**。手書き入力UIの内部表現として使える |
| `.atdoc` の独自バイナリ形式 | 再現不要。SQLiteまたはJSON/CBORベースの新フォーマットを新規設計 |
| mazecネイティブ認識エンジン | **流用・リバースエンジニアリング不可**(プロプライエタリ)。代替手段を選定する必要あり(下記) |
| 独自TCPテキストプロトコル(教室協働) | 再現不要。WebSocket + JSON等、標準的な方式に置き換え |
| MetaMoJi自社サーバー(cabinet.7knowledge.com / mps.metamoji.com / cosmos API) | **接続不可**。教室協働・クラウド同期を実装するなら自前バックエンドを新規構築する前提 |
| PDF独自パーサ/ライタ | Rustエコシステムの既存クレート(例: `pdf`, `lopdf`, `printpdf` 等)や `pdfium` バインディングを利用する方が効率的。ゼロから自作する必要性は低い |
| 動画トランスコード・波形編集 | デスクトップでは `ffmpeg` を外部プロセス/バインディング経由で使うのが現実的(モバイル特有の制約がないぶんシンプルにできる) |

## 3. 手書き認識エンジンの代替候補

PC向けなので選択肢はモバイルより広い。

- **Windows Ink**(`Windows.UI.Input.Inking` 系API): Windows OS標準、無料、オンデバイス。Tauri(Rust)からWindows Runtime APIを呼ぶ形になる。Windows専用。
- **Google ML Kit Digital Ink Recognition**: オンデバイス・無料・多言語対応。ただしAndroid/iOS向けSDKが中心で、デスクトップ(Rust/Tauri)からの利用は追加の工夫が必要な可能性がある(要調査)。
- **MyScript**: 商用SDK、mazecに近い認識精度・カスタム辞書機能。ライセンス費用が発生する。
- **クラウドOCR/手書き認識API**(要調査): オフライン要件次第では選択肢になり得るが、オフライン動作という元アプリの強みを失う。

→ どの方式を採用するかは要件次第(オフライン必須か、対応言語、コスト)なので、ユーザーとすり合わせが必要な論点。

## 4. 技術スタック案(既存スキャフォールドを前提に)

- フロントエンド: React + TypeScript(既存の `metamoji/src` を継続利用)
- 描画: Canvas 2D または WebGL(`<canvas>` + 独自レンダラ、もしくは `Konva.js`/`Fabric.js` 等の既存キャンバスライブラリを検討)
- バックエンド(Rust側 `src-tauri`): ローカルファイルI/O、SQLiteでのノートメタデータ管理、PDF入出力、(将来的に)同期クライアント
- ローカルDB: `rusqlite` などでSQLite管理

## 5. ユーザーとすり合わせたい論点

- 上記スコープ A/B/C のどこまでを目指すか(まずはAから着手するのが妥当と考えている)
- 手書き認識は必須機能か、なくても許容できるか(まずは手書き「入力・保存・表示」のみでも成立する)
- `.atdoc` で作成済みの既存ノート資産をこの新アプリに取り込みたいか(取り込みたい場合、`.atdoc` フォーマットのリバースエンジニアリング作業が追加で必要)
- クラウド同期・教室協働機能をどこまで再現したいか(自前サーバーの新規構築が前提になる)

これらが固まり次第、具体的な機能要件定義・データモデル設計・実装計画を作成する。
